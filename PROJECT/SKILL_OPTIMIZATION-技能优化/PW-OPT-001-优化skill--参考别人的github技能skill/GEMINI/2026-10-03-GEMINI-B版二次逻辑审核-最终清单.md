## 二、B-01～B-26 逐项审核

### 1. 资产与模式管理

**B-01｜H3 Mode Detection Layer — ACCEPT**

自动判断 Ref2VA / T2VA / I2VA / FL2VA / L2VA 等生成模式，并区分 character/reference asset、environment/style reference、first/last frame、storyboard/keyframe。存在歧义时询问最小必要问题，不因图片存在就自动将其视为 frame anchor。

**B-02｜Reference Role Mapping Layer — ACCEPT**

明确 Identity、Clothing、Environment、Composition、Motion、Camera、Audio、Style、Frame Anchor 等职责及作用域，防止参考图特征无边界扩散。

**B-03｜Reference Conflict Resolver — MODIFY**

保留冲突解决思想，但 Conflict Table 必须属于 Compiler 内部 Intermediate Representation（IR）阶段，不应直接输出给 H3。最终物理 Prompt 只交付已经解决冲突的唯一属性描述。

**B-04｜Retention Analysis 2.0 — MODIFY**

升级为 Reference Retention Matrix / Pre-flight Inspection。用于编译前校验和系统内部 State，不把 `fully_preserved` 等元数据标签直接吐入 H3 物理 Prompt。

### 2. 时间与动作控制

**B-05｜Temporal State Ledger — ACCEPT**

每个 Shot 记录 subject / pose / object / environment / camera / audio / newly introduced state / carried-over state，以增量方式保证跨 Shot 状态连续。

**B-06｜One Dominant Action per Shot — ACCEPT**

每个 Shot 只允许一个同等级 Dominant Action；可以存在 secondary micro-actions、表情、呼吸和轻微手部动作，但不能出现第二个同等级主动作。必要时拆分 Shot。

**B-07｜Action Vector Layer — ACCEPT**

动作可拆为 direction、amplitude、frequency、contact、trajectory、speed、acceleration/deceleration、start state、end state。但必须遵守 **Minimum Sufficient Physical Description**，避免为了物理精确而无限增加文字。

**B-08｜Camera Kinematics Layer — ACCEPT**

Camera State 与 Subject Action 分离，包括 camera type、viewpoint、framing、movement、amplitude、speed、stabilization、depth behavior 等，避免 Camera / Subject 语义耦合。

### 3. 空间、密度与视觉参数

**B-09｜Spatial Geography Layer — MODIFY**

采用自适应 Level 0～Level 2：普通位置关系 → foreground/midground/background → 方向/比例/遮挡关系。Level 3 复杂 3D spatial graph 降级为 **RESEARCH ONLY**，不进入默认 B 规则。

**B-10｜Adaptive Prompt Density — ACCEPT**

建立 Prompt Density Budget，根据任务复杂度动态决定信息密度，而不是默认“越详细越好”。目标是避免 Attention Overcrowding。

**B-11｜Creative Enhancement Gating — ACCEPT**

建立 Requirement / AI Proposal 明确边界。用户已指定故事时严格执行；用户明确要求创意帮助时才允许 Narrative Creative Enhancement；粗略想法可提出候选方案，但 AI Proposal 不能自动升级为 User Requirement。

**B-12｜Narrative Creative Enhancement — ACCEPT**

作为独立的 Ideation 模式，与 Prompt Compilation 解耦。流程：User Idea → Narrative Brainstorm → Candidate A/B/C → User Selects → Prompt Compilation。只有用户确认的创意才能进入最终 Prompt。

**B-13｜Environmental Reactivity Controller — ACCEPT**

默认 OFF。只有用户明确要求、环境反应是剧情核心，或环境反应对动作执行确有实际帮助时才启用；否则保持 Background Stability。

**B-14｜Visual Texture Budget — ACCEPT**

优先 Reference Image。已有 Reference 时压缩 cinematic lighting、film grain、volumetric lighting 等文本质感词；无 Reference 时才补必要视觉参数，以降低 Style Drift。

### 4. 架构、PATCH 与验证

**B-15｜Camera / Subject / Environment 三层解耦 — ACCEPT**

Prompt 内部形成 CAMERA / SUBJECT ACTION / ENVIRONMENT 三个独立层。三者可以存在关系，但不混成一个难以 Debug 的长句。

**B-16｜PATCH Architecture — ACCEPT**

正式支持 PATCH_CAMERA、PATCH_ACTION、PATCH_CHARACTER、PATCH_ENVIRONMENT、PATCH_AUDIO、PATCH_TIMING、PATCH_REFERENCE 等局部修改模式。

**B-17｜Minimal Semantic Change — ACCEPT**

PATCH 只修改用户指定部分。非目标层必须保持不变，避免一次局部修改导致全 Prompt 语义抖动。

**B-18｜Shot-Level Verification — ACCEPT**

每个 Shot 输出前检查 Dominant Action、Subject、Reference、Camera、Environment、State Continuity、Timestamp 和是否引入未经授权的新剧情。

**B-19｜Global Verification — ACCEPT**

最终 Prompt 输出前执行全局 Contract 检查：Reference label consistency、Timeline、Duration、State Continuity、Camera/Action separation、Semantic drift、Output format 等。

**B-20｜Debug Trace — MODIFY**

保留完整溯源机制，但只存在于系统内部日志 / Meta State / `[DEBUG_TRACE]` 中。最终发送给 H3 的物理 Payload 必须剥离 Debug Trace，避免浪费 context / token budget。

### 5. 实验治理与多模式编译

**B-21｜Evidence / Candidate Status — ACCEPT**

新增机制必须拥有生命周期状态：RESEARCH → EXPERIMENTAL → VALIDATED → PROPOSED → FROZEN。防止未经验证的实验技巧自动成为永久规则。

**B-22｜A/B Experimental Isolation — ACCEPT**

B 与 A 在实验期间完全独立。测试前不得使用 A 的最终优化规则反向约束 B。

**B-23｜Mode-Specific Optimization — ACCEPT**

根据 Ref2VA / T2VA / I2VA / FL2VA / L2VA 的不同 conditioning 与任务特点进行模式分流，而不是所有模式强行使用同一套增强机制。

**B-24｜Reference Asset Wiring Awareness — ACCEPT**

保持 Reference Mapping 与 Physical Wiring Order 的双层意识：语义上 Image 1 的职责与物理输入 socket 顺序分别管理，二者不能混为一谈。

**B-25｜Output Compiler Layer — ACCEPT**

将 Prompt 生成拆成确定的 Compiler Pipeline：Ideation → Semantic Plan → Reference Map → Shot Plan → Physical Execution Plan → H3 Format Compiler → Verification。避免一步到位生成复杂 Prompt。

**B-26｜B 版总体原则 — ACCEPT**

最高指导原则：用户语义优先、Reference 约束优先、H3 可执行性优先、Minimum Sufficient Description、创意与编译解耦、Camera/Action/Environment 解耦、实验机制与正式规则解耦、所有新增能力可追溯/可测试/可回滚。

## 四、Gemini 本次最终结论

Gemini 判断：GPT 的 B-01～B-26 清单已经从单纯的 Prompt 词汇优化扩展到完整的 **Prompt Compiler Architecture**，尤其补足了 Mode 分流、Reference Conditioning、Prompt Density Budget、PATCH、Verification、Debug Trace、Mode-Specific Optimization 与 Output Compiler 等工程层能力。

- 不修改正式 V1-5 Baseline；
- 不修改 A 组；

- 最终以 H3 实测结果和用户最终批准决定是否进入下一阶段。
