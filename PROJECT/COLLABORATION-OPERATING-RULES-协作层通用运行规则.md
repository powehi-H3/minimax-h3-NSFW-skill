# COLLABORATION-OPERATING-RULES — 协作层通用运行规则

## 目的

将“任务完成后必须明确标记状态，并保留完成记录”的做法提升为整个项目的通用运行规则。

## 通用规则：任务生命周期必须可追溯

任何进入 GitHub 项目并被定义为一个独立任务的工作，都必须具有明确的生命周期状态。

至少使用以下状态之一：

- `PLANNED` — 计划中
- `IN_PROGRESS` — 进行中
- `REVIEW` — 审查中
- `TESTING` — 测试中
- `AWAITING_APPROVAL` — 等待用户批准
- `COMPLETED` — 已完成
- `ARCHIVED` — 已归档

## 完成时必须做什么

当任务已经达到用户确认的完成条件时，必须完成以下步骤：

1. 在任务目录或任务主记录中明确标记：`STATUS: COMPLETED`。
2. 创建或更新 `COMPLETION-REPORT-完成报告.md`。
3. 在完成报告中记录：
   - 任务名称
   - 任务目标
   - 实际完成步骤
   - 最终产出文件
   - 关键决策 / 修正
   - 哪些文件被修改
   - 哪些文件明确没有修改
   - 测试 / 验证结果（如有）
   - 用户最终确认状态
   - 后续是否还需要其他 AI 参与
4. 如果任务已经结束且不需要继续修改，可标记为 `ARCHIVED`；但不得删除完成记录。
5. 后续 AI 进入项目时，应能够仅通过任务状态和完成报告判断该任务是否已经结束，以及自己是否需要参与。

## 已完成任务不得被重新打开式修改

如果一个任务已经标记 `COMPLETED`，其他 AI 不应因为看到该任务而自动重新 Review、优化或改写。

如发现新的问题，应建立一个**新的任务**，并引用原任务作为来源。

例如：

```text
TASK-A  → COMPLETED
             ↓
发现新问题
             ↓
TASK-B  → 新任务
```

不得直接把 TASK-A 改成一个混合任务。

## 多 AI 协作规则

当一个任务完成后：

- 已参与 AI：保留历史记录。
- 未参与 AI：原则上只需要读取完成报告了解结果。
- 后续需要继续研究时：创建新的任务，而不是修改已完成任务的历史记录。

## 原始记录与完成报告必须并存

`SOURCE / CONVERSATION-FULL / ORIGINAL` 等原始记录用于保留事实来源。

`COMPLETION-REPORT` 用于说明任务最终做到了什么。

二者不能互相替代。

## 周期性任务对话检查点：Task Conversation Checkpoint

### 目的

任务对话可能包含关键决策、实验假设、AI 分歧和用户批准信息。仅依赖最终报告可能导致中途的重要上下文丢失。

因此，所有持续进行中的任务应采用**周期性对话检查点机制**。

### 默认触发条件

当同一任务累计约 **3–5 次有实质内容的任务对话 / 讨论轮次** 后，当前负责记录的 AI 应主动检查一次 GitHub 任务对话归档。

这里的“实质内容”包括：

- 新决策
- 新研究结论
- 用户对方案的确认 / 否决
- AI 之间的重要分歧与解决
- Prompt / Skill / Experiment 的版本变化
- 新的实验假设
- 新的测试结果
- 对任务范围、约束或职责的改变

纯寒暄、重复确认、简单“好 / OK / 继续”等不计入检查点。

### 检查点执行步骤

达到 3–5 轮后：

1. 判断当前任务及任务目录。
2. 找到该任务的 `CONVERSATION-FULL / TASK-CONVERSATION / 对话归档` 文件；若任务尚无对话归档，则创建一个。
3. 将最近一个检查点以来的**重要对话事实**追加进去。
4. 保留：
   - 用户原始决定
   - AI 各自的独立意见
   - 已确认的结论
   - 尚未确认的候选
   - 任务状态变化
5. 不得把 AI 建议写成用户批准的决定。
6. 不得覆盖历史归档；原则上采用追加方式并保留时间 / 检查点标记。
7. 更新任务 `PROGRESS`（如果任务有该文件）。
8. 如发生重大决策，即使未达到 3–5 轮，也应立即同步，不必等待下一检查点。

### “自动”机制的实际含义

这是一个**工作流自动化规则**，不是后台定时器。

也就是说：

- AI 在当前会话中可以维护任务对话轮次计数。
- 达到阈值时，应主动执行 GitHub 同步。
- 如果会话突然结束、AI 下班或工具不可用，下一次接替 AI 应根据任务状态判断是否存在未同步的对话内容。
- GitHub / 模型本身不会在用户完全离线时凭空读取未来对话，因此不能把该规则理解为真正的后台自动监听。

### 立即同步例外

以下情况不需要等 3–5 轮：

- 用户明确说“这个很重要，不能丢”。
- 用户做出正式批准 / 否决。
- 任务范围发生变化。
- 版本状态发生变化。
- AI 角色或接替关系发生变化。
- 产生新的关键实验结论。
- 发现可能影响整个项目的通用规则。

### 防止文档膨胀

周期性归档不是逐字复制全部聊天记录。

默认保存**结构化的重要信息**；如果用户明确要求“完整对话原样保存”，才建立或更新 `CONVERSATION-FULL` 原文档。

### 与 AI 下班机制配合

如果某 AI 在检查点之前突然不可用：

- 优先保存当前任务状态；
- 如有重要未同步内容，接替 AI 应在获得当前对话内容后尽快补写检查点；
- 不得因为 AI 暂时不可用而丢弃尚未完成的任务上下文。

## 对现有任务的适用

本规则同样适用于：

- Prompt Writing / 提示词编写
- Prompt Optimization / 提示词优化
- Skill Optimization / 技能优化
- External Skill Research / 外部 Skill 研究
- AI Collaboration / 协作层任务
- 未来新增的其他任务类型

## 与 V1-5 Skill 的关系

本文件属于**项目协作层通用运行规则**。

它不修改、不扩展 V1-5 H3 Prompt Skill 的生成规则。

如果未来需要修改 V1-5 Skill，必须按照独立 Skill Optimization 任务流程处理，并经过用户批准。
