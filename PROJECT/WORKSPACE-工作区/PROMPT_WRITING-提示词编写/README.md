# PROMPT_WRITING — 提示词编写

用于从零开始编写新的 MiniMax H3 提示词。

## 标准流程

1. User 提供需求与可用素材。
2. GROK 负责形成第一版可执行提示词。
3. GPT 负责结构、语义边界、官方规则一致性和风险检查。
4. Gemini 负责独立的提示词表达、可执行性和质量复核。
5. GROK / GPT / Gemini 根据测试结果继续迭代。
6. User 最终确认。
7. 确认后的成品复制到 `PROJECT/LIBRARY-正式库/PROMPTS-正式提示词/`。

## 单任务建议结构

每个具体任务使用独立文件夹，例如：

```text
PW-0001-任务名称/
├── 00_BRIEF-需求.md
├── 01_GROK_DRAFT-初版.md
├── 02_GPT_REVIEW-审查.md
├── 03_GEMINI_REVIEW-审查.md
├── 04_TEST_RESULTS-测试结果.md
├── 05_FINAL-最终版.md
└── 06_DECISION-收录决定.md
```

## 核心纪律：SOURCE 原始资料不可净化、不可覆盖

### 1. 原始资料是最高优先级的工作证据

用户、GROK、Gemini 或其他项目参与者提供的原始 Prompt、原始对话、素材说明、测试记录等，在进入项目工作区后必须按原始内容保存。

**任何 AI 不得擅自对 SOURCE 做“净化”、弱化、删减、润色、重写、改写、替换或重新解释，然后再把处理后的版本冒充 SOURCE / 原稿。**

特别是 `01_GROK_DRAFT-初版.md`：如果它被标记为 GROK 原稿，则必须保持 GROK 实际提交版本的原始内容。后续任何 AI 的意见都不得直接覆盖它。

### 2. REVIEW 与 SOURCE 必须完全分离

审查意见只能写入对应的 REVIEW 文件，例如：

```text
01_GROK_DRAFT-初版.md   ← 原始稿，只读证据
02_GPT_REVIEW-审查.md    ← GPT 独立意见
03_GEMINI_REVIEW-审查.md ← Gemini 独立意见
```

审查者不得为了方便审查而直接修改原始稿。

### 3. 新版本必须产生新文件

如果经过用户批准，需要采用某项修改，则创建新的 Draft / Candidate / Revision 版本。

**不得用修改原稿的方式生成新版本。**

版本关系必须能够追溯：

```text
SOURCE / 原稿
    ↓
独立 REVIEW
    ↓
用户批准采用的修改
    ↓
DRAFT-V2 / REVISION-V2
    ↓
测试
    ↓
下一版本
    ↓
USER FINAL APPROVAL
```

### 4. 不得把 AI 自己的限制变成项目规则

项目工作区记录项目真实资料、协作意见和版本历史。

任何参与 AI 的个人输出限制，不得被擅自改写成“项目禁止保存 / 项目禁止研究 / 项目必须删除”的通用项目规则。

如果某个 AI 无法执行某项任务，它应当保持自己的职责边界；其他参与者仍按照各自实际能力和项目协作协议工作。不得因此篡改、净化或伪造其他参与者的 SOURCE。

### 5. 原始内容、审查意见、最终版本必须可追溯

任何参与者都应该能够回答：

- 这是谁的原稿？
- 原稿是什么？
- 谁提出了什么修改意见？
- 哪些意见被采用？
- 谁批准了修改？
- 哪个版本最终通过？

禁止出现“某 AI 先私自改写原稿，再让其他 AI 审查改写后的版本，却把它称作原稿”的情况。

## 重要规则

- 工作区里的版本不是正式资产。
- 没有 User 最终确认，不进入正式提示词库。
- 不因为素材中出现某个元素就自动加入最终提示词，除非 User 要求参考。
- 如果 User 要求只改某一点，其余内容应尽量保持。
- **SOURCE 原稿永远优先保存；Review 永远旁路；新修改永远产生新版本。**
